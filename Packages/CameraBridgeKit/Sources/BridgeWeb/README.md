# BridgeWeb

The web interface of Camera Bridge OS, as portable Swift: an HTTP/1.1 server over the injected `NetworkTransport`, the JSON API
(`/api/v1`), password and session handling, static file serving and an SVG QR code encoder. It depends on the engine and on
`Crypto` only; every test runs on a Mac against a fake backend, the in-memory transport or the real engine. The API contract is
in `docs/linux/ARCHITECTURE.md`; the interface itself is `linux/web/`.

## Layout

| File | What |
|---|---|
| `HTTPServer.swift`, `HTTPTypes.swift` | Keep-alive and pipelined requests (parsed by BridgeSupport's `HTTPRequestParser`), head, body and time limits, connection limits per peer, chunked streaming answers (server-sent events, multipart JPEG) that end when the client leaves; a stream that throws ends without the last chunk (a failed download, not a finished one); a stream of known size (`contentLength`: a clip) is sent with `Content-Length`; `HTTPResponse.onDiscard` runs when a stream's body never runs (HEAD, a head that could not be sent), so the routes give back their live, event and archive slots exactly once (`ReleaseOnce`) |
| `WebApp.swift`, `WebApp+Routes.swift`, `WebApp+Bridge.swift` | The route table and handlers; Host, Origin, session and CSRF checks; security headers |
| `AuthStore.swift`, `Security.swift` | First-run setup, PBKDF2-HMAC-SHA256 (600,000 rounds, per-password salt), 256-bit session tokens kept as SHA-256 hashes in `<data>/web/auth.json` (0600), login rate limiting, constant-time comparison |
| `CameraSetup.swift`, `CameraTypeCatalog.swift`, `HostInput.swift` | The Mac app's Add Camera wizard as a stateless service: the same types, words and checks |
| `EventHub.swift`, `LogFeed.swift` | Server-sent events from the engine's observable state; the live log |
| `StaticFiles.swift` | The interface's files: content types, ETag and 304, traversal-proof paths |
| `QRCode.swift` | QR Code encoder (byte mode, versions 1 to 10, levels L and M) drawing SVG |
| `BridgeBackend.swift`, `SystemControl.swift` | The seams: `EngineBackend` wraps `BridgeEngine`; `SystemControlling` is the operating system under the bridge |
| `WebApp+NVR.swift`, `WebApp+NVRStorage.swift`, `WebApp+NVRCatalog.swift`, `WebApp+NVRMedia.swift`, `WebApp+NVROptimize.swift`, `ArchiveLocation.swift` | The NVR routes: the route table (`WebApp.archiveRoutes`), admission slots, the gates and the one error mapping; storage and the Record switch; catalog, activity and events; fragment plans, video-only fragments, init segments and key pictures; the optimizer and its undo; the places the page may offer for recordings (`ArchiveLocation`: the browser sends the id and never the path) |
| `WebApp+Sky.swift` | The Sky Watcher's routes (`WebApp.skyRoutes`: the night's log, an entry's picture, one-tap corrections, "Find a feed"), what `PATCH settings` and `PATCH cameras/:id` take for it (`SkyPatch`, `SkyDetectorPatch`) and what the page reads (`SkyNightResource`, `SkyEntryResource`, `SkySettingsResource`) |
| `WebApp+HLS.swift`, `HLS/*.swift` | HLS for AirPlay and CarPlay (`WebApp.hlsRoutes`): `POST hls/tickets` and `GET hls/:ticket/:file`, the ticket store (`HLSTickets`), the live packager and segmenter, the playlist writer and the recorded-range planner; see "HLS tickets" below |
| `Away/*.swift`, `WebApp+Away.swift` | Away from home (`WebApp.awayRoutes`, seven routes): `AwayService` (the actor that keeps the devices, the tunnel's subnet and the away name, and asks the system to match them), `AwayRules` (the subnet, the stable address, what counts as away, the card's states, the WireGuard configuration), `AwayState`, `AwayKeyPair`, `AwayDocuments` (the card and the tunnel document), `AwaySystem` (`AwayRequest`, `AwayStatus`) and `AwayNetwork` (`AwayAddress`); see "Away from home" below |
| `ViewerPairing.swift`, `WebApp+Viewers.swift`, `ViewerAnnouncer.swift` | The Apple TVs, iPhones and iPads (one pairing for all): the pairing requests as a value with no clock of its own (`ViewerPairing`: codes of 8 letters without vowels, 10 minutes, the limits; in memory only; `AuthStore` keeps the TVs and the box's identity); the routes that pair, list and remove them and `GET viewer` (`WebApp.viewerRoutes`); and the `_camera-bridge._tcp` announcement through the platform's `ServiceAdvertiser` (`ViewerAnnouncer`) |

## Additions beyond the contract

Apple TVs (2026-11-02, docs/CONTRACT_CHANGES.md; spec docs/superpowers/specs/2026-11-01-apple-tv-app-design.md): an Apple TV asks the box for a code, the signed-in owner types it into Settings, and the TV is handed a key that can only watch and move cameras that pan and tilt. `AuthStore` keeps the TVs and the box's identity in `auth.json` beside the sessions (both optional in the file, so one written by 0.1.131 still reads): `AuthStore.ViewerInfo` (`id`, `name`, `device`, `created`, `lastSeen`, `address`; never the key), `AuthStore.bridgeID()` (16 random bytes as 32 lowercase hex, made the first time anything asks and kept until a factory reset), `AuthStore.beginPairing(name:device:address:)` (answers `AuthStore.PairingStart`: `request`, `secret`, `code` as "BCDF-GHJK", `expiresIn` 600 and `interval` 2; throws `AuthStore.PairingFailure.busy(retryAfter:)` for a 4th open request from one address (an IPv6 /64 counts once) or a 21st in all), `AuthStore.approvePairing(code:)` (the code in any case, with or without the dash: the TV is added and saved at once and the box keeps only the SHA-256 of its key; throws `AuthStore.PairingFailure.noSuchCode` for a code that is unknown, ended, used or not a code, `.tooManyViewers` at 20 TVs, and `AuthStore.Failure.storageFailed` or `.unreadable`), `AuthStore.pairingStatus(request:secret:)` (`AuthStore.PairingStatus`: `.waiting`, then once `.approved(token:viewer:)` with the key, then `.gone`), `AuthStore.viewers()` (the one used last first), `AuthStore.viewer(token:address:)` (the TV a key belongs to, noting when and from where it was used; nil for a key unused for a year), `AuthStore.removeViewer(id:)` and `AuthStore.isViewerListed(_:)`. The requests live in memory only (`ViewerPairing`, internal): codes of 8 letters from `BCDFGHJKLMNPQRSTVWXZ` that spell no word, a request lasts 10 minutes, an approved one waits at least a minute for its TV, and a TV whose key nobody collected is taken out of the list again.

Apple TVs, the routes (`WebApp+Viewers.swift`, `WebApp.viewerRoutes`; docs/linux/ARCHITECTURE.md, "Web API"): `POST viewers/pair {name?, device?}` and `POST viewers/pair/status {request, secret}` are open, since all they do is make a code and hand the key to the TV that waited with it (429 `too_many_pairings` with `Retry-After`; 404 `pairing_gone` once a request is over or was never there); `POST viewers/approve {code}` (201 `{viewer}`; 404 `no_such_code`, 409 `too_many_viewers`, 500 `storage`), `GET viewers` and `DELETE viewers/:id` (204, or 404) need the owner's session; `GET viewer` is the one answer a TV draws its screens from, `{bridge: {id, name, version, secureURL}, cameras: [{id, name, kind, enabled, connection, motion, recordingNow, panTilt, zoom, sound, main, sub, lastEvent}]}` in the owner's order, every key always there (null where not known) and no address, user name, stream URL, setting, token or setup code in it.

Apple TVs and iPhones, the access level (`Route.Access.viewer`, internal): fifteen routes (`GET viewer`, `GET cameras/:id/snapshot`, `GET live`, the seven NVR routes that read recordings, `POST cameras/:id/pan-tilt`, `POST hls/tickets` and the three `viewer/away` routes: `POST`, `GET` and `DELETE`) take either a browser's session, as before, or an Apple TV's or iPhone's `Authorization: Bearer <key>` with no cookie and no `X-CSRF-Token`; the key is never accepted in the address and on no other route (see "Security notes"). `WebConfiguration.viewerRecheckInterval` (default 5 s, never under 100 ms) is how often a TV's live view looks whether the TV is still added: one removed while it watches loses its picture within that time.
HLS tickets (2026-11-06, docs/CONTRACT_CHANGES.md; spec docs/superpowers/specs/2026-11-06-ios-carplay-app-design.md, "The box side"; for the iPhone, iPad and CarPlay apps, which play it with AVPlayer, AirPlay and CarPlay; away from home only through Away from home, below) (`WebApp+HLS.swift`, `HLS/HLSTickets.swift`): `POST hls/tickets` (a viewer route) trades a TV's key (or a browser's session) for a ticket that opens one camera, read-only, at `GET /api/v1/hls/<ticket>/<file>` (open; the deliberate exception to "no token in an address", the viewer key itself stays refused there). A ticket is 32 random bytes as hex, in memory only, found by constant-time comparison, ending 5 minutes after its last use or 6 hours after it was made; a viewer holds 8 (the oldest goes first); a TV removed from the list, or a browser signed out (sign-out, removal from the list, a password change), loses its tickets at its next request (`AuthStore.isSessionListed`). Tickets end on `WebConfiguration.uptime`, a clock nobody sets (2026-11-11: they ended on the time of day, so a clock set forward ended every open one and one set back made them last longer); `WebConfiguration.now` only cuts a recorded range at now. A live ticket's files come from the camera's packager (`HLS/HLSLivePackager.swift`), which one ticket starts and later ones share per camera, stream and sound: it takes one live slot (none free is 429 `too_many_streams` at the ticket route), cuts the same `LiveMP4Remuxer` parts as `GET live` into segments in memory, and stops 30 s after its last request (`WebConfiguration.uptime`), or sooner when a removed viewer's next file request finds no other viewer using it, or when a ninth ticket pushed out the viewer's last ticket on it and nobody else uses it (`HLSLivePackagers.release`; 2026-11-11: a device minting across cameras could otherwise hold every live slot), so an on-demand sub stream can stop. A packager with sound whose camera's "Camera audio" switch is turned off stops when the camera restarts for it, instead of subscribing again, so the player's next ticket has no sound (`HLSLivePackager.keepsItsSound`); `GET live` reads the switch again before each new subscription of a camera it was asked to hear, both ways (`soundSwitch`), and the engine sends no sound for a camera whose switch is off whatever is asked (`BridgeEngine.liveVideo`). A ticket plays only the packager it was minted against, since a newer one numbers from 0 again: once that one has stopped the ticket gets 404 and the player takes a new one. A first playlist waits up to `WebConfiguration.hlsFirstPlaylistWait` (18 s, under AVPlayer's own 20 s per playlist) for three segments, what a player must start on not to freeze, then is 503 with `Retry-After`; a master that has one segment to write it from answers 200 instead, so a camera with long key intervals gets a second 18 s for the media playlist. A recorded ticket (`{camera, kind: "recorded", from, to}`, at most 2 hours) is planned once when it is made (`HLS/HLSRecorded.swift`) and served as a video-on-demand playlist: `index.m3u8`, `media.m3u8`, `init-<n>.mp4` and `seg-<n>.m4s`, each segment a key fragment and the fragments after it, so it starts on a key picture, with the camera's sound when its Camera audio switch is on. A range with nothing recorded is 404 `gap`, a longer one 400 `range_too_long`, and a file read takes an archive slot (429 `busy`). The ticket in the path is a deliberate exception to "no token in an address", stated in docs/linux/ARCHITECTURE.md, "Security"; the viewer key itself stays refused there.

Apple TVs, the announcement (`ViewerAnnouncer`, internal): `WebConfiguration.viewerAdvertiser` (default nil: nothing is announced) registers `_camera-bridge._tcp` through the platform's `ServiceAdvertiser` once the web port listens, without ever delaying the start. The instance name is the bridge's name cut to 63 bytes of UTF-8 on a character boundary ("Camera Bridge" when nothing is left), the port is the web port, and the TXT record is `id` (the box's identity, `GET viewer`'s `bridge.id`), `name` (the bridge's name; cut to 250 bytes when `name=` and the name together would pass a TXT entry's 255), `v` (the version) and `api=1`. A saved name registers again, a registration that fails is tried again after 1 s, doubling up to 60 s, and the old `_http._tcp` announcement for browsers stays as it is. The daemon hands the advertiser over on Camera Bridge OS only (BridgeDaemon README).

Apple TVs, the key picture (2026-11-02): `GET nvr/cameras/:id/keyframe?at=&picture=1` answers the first picture of the key fragment alone, as a `moof` and `mdat` of one sample with no sound (`X-CB-Part` is the fragment's, its `end` where the picture ends), for a thumbnail or an Apple TV that scrubs; `picture=0` or none is the whole key fragment as before, and any other value is 400 `invalid` with the field `picture`. Everything else is the key fragment's answer, and `maximumSegmentBytes` applies to the picture sent. The page's thumbnails (`linux/web/js/nvr/thumbs.js`) ask for it.

## Security notes

- Only IP addresses, `localhost`, `*.local`, `*.home.arpa`, names without a dot and `allowedHosts` are served (DNS rebinding).
- A request that changes something needs an `Origin` that matches `Host` (or `Sec-Fetch-Site: same-origin`), the session's
  `X-CSRF-Token` and `Content-Type: application/json`.
- The session cookie is `HttpOnly; SameSite=Strict; Path=/` (and `Secure` behind a TLS front end).
- The `viewer` routes (`Route.Access.viewer`: `GET viewer`, `GET cameras/:id/snapshot`, `GET live`, the seven NVR routes a TV plays recordings
  with, `POST cameras/:id/pan-tilt`, `POST hls/tickets` and the three `viewer/away` routes) also take an Apple TV's key as `Authorization: Bearer <key>` (`WebApp.bearerToken(in:)`, the reading
  `GET monitor` uses too), with no cookie and no `X-CSRF-Token`; the `Origin` and JSON checks still apply. A key that is there decides alone:
  a wrong, expired or removed one is `401 viewer_key` with `WWW-Authenticate: Bearer` (`WebApp.viewerKeyRefused`), even beside a valid
  session cookie, and no cookie is cleared; the handler then sees the TV (`RequestContext.viewer`) and no session. Without the header a
  viewer route applies the session rules unchanged. `token=` or `access_token=` in a viewer route's query is `400 invalid` (field `token`,
  `WebApp.keyInTheAddress`), even with a good header. Every other route never looks at a key: one that needs a session answers `401 unauthorized`, an open one answers as it would anyone.
- An Apple TV's key is 32 random bytes; `auth.json` keeps only its SHA-256 (`AuthStore.viewer(token:address:)` compares hashes in constant
  time and records when and from where the key was used). A key unused for a year stops working, a password change keeps the TVs, a factory
  reset removes them. Removing a TV refuses its key at once, and a live view it has open ends within `WebConfiguration.viewerRecheckInterval`
  (5 s): `GET live` asks `AuthStore.isViewerListed(_:)` that often while a TV watches.
- What gives root or erases asks for the administrator password again (`WebApp.confirmPassword`, through the sign-in limiter): SSH on, a
  factory reset, installing to a disk, erasing a recording or archive drive. `403 password_required` / `403 wrong_password` / `429`.
- Every error answer is `{error, code, message, field?}`; `code` repeats `error`.
- Recordings: every NVR route needs a session, and the seven reading ones a TV plays recordings with (catalog, activity, events, fragment
  plans, fragments, init segments, key pictures) also take a TV's key. The browser sends ids and times, never a path (a location is an opaque id from `WebConfiguration.archiveLocations`, a fragment
  id is opaque). Footage is `Cache-Control: no-store`, an answer is at most `maximumSegmentBytes`, there is no `Range` support and HEAD on a media route is 405. Archive
  requests are admitted at most `maximumArchiveReads` in all and `maximumArchiveReadsPerAddress` per peer address (`429 busy`, `Retry-After: 1`), and no handler touches the
  disk on the cooperative pool.
- The Content-Security-Policy allows `media-src 'self' blob:` and nothing else beyond what the interface already had: the player's MediaSource URL is a `blob:`; no script, frame, worker or remote host is widened.
- Camera passwords, cloud sources and API keys go to the engine's secret store and never into an answer, the log or a file of the web
  interface.

Notifications (2026-10-22, docs/CONTRACT_CHANGES.md; `NotificationLog.swift`, `WebApp+Notifications.swift`): the log of everything that was a notice, in `notifications.json` in the data directory (private file, written atomically; the last 500 entries or 90 days). An entry is added when a notice first appears or changes (`NoticeResource.key`: its id, title and camera, so other figures in the text are not a change); a state notice that goes away and comes back is a new entry, an event (the Internet guard's, `kind` `internetGuard`) is logged once ever (the keys of the last 1000 events are kept). The log is brought up to date by the event hub on every change it sees (and every 5 s while nobody listens) and by each of the routes. `GET notifications` lists it (`{unread, notifications}`, newest first); `POST notifications/shown` hands the entries of the current notices not yet shown as a toast to the caller and marks them shown, so each is shown once by one browser (the phone and the Mac agree; nothing is kept in the browser); `POST notifications/read {ids?}` marks entries read, or all. An entry: `id, key, noticeID, kind, category (security|recording|cameras|system), severity, title, detail, cameraID, cameraName, action, date, read, toasted`. `status.notices` items carry `category` and `key` too, and no longer a `cameras` list.

A damaged configuration (2026-10-31, docs/CONTRACT_CHANGES.md; engine-core review F4): while the engine has a `configurationRecovery` nobody dismissed, the notices start with `{id: "configuration-recovered", kind: "configurationRecovered", severity: "warning", category: "system", action: "dismiss"}`, titled "Settings Restored From a Backup" when the copy kept before the last change took its place (`BridgeOverview.configurationRestoredPrevious`) and "Settings Could Not Be Read" when the bridge started without cameras. `POST notifications/dismiss {id}` puts it away (`BridgeBackend.acknowledgeConfigurationRecovery()`, default: nothing) and answers `{dismissed: true}`; any other id is a 400 (those notices go away by themselves). The page shows a Dismiss button for the action `dismiss`.

A camera that is offline or not recording (2026-10-31, docs/CONTRACT_CHANGES.md; improvement engine-core I2 / engine-events I1): a turned-on camera whose status has been `offline` for 5 minutes (`CameraStatus.connectionSince`, `offlineSince` while offline; `NoticeResource.cameraTroubleAfter`) is the notice `{id: "camera-offline-<camera id>", kind: "cameraOffline", category: "cameras", severity: "warning", title: "<name> Is Offline", detail: "Camera Bridge hasn’t reached <name> since 9:40 PM: <reason>." (+ " Its recording has a gap until it is back." when it records; the time in the bridge's zone, with the date when it is not today), cameraID, cameraName, date: when it went offline, action: "open-camera"}`. A camera that is online with its Record switch on but whose recorder has waited 5 minutes (`CameraStatus.nvrWaitingSince`) is `{id: "camera-not-recording-<camera id>", kind: "cameraNotRecording", category: "recording", title: "<name> Isn’t Recording", detail: "Its Record switch is on, but nothing has been recorded since <time>. <the recorder's reason>"}`. Both come first after the configuration notice; they are state notices: gone when the camera is back, told again at its next outage. `GET cameras` carries `status.connectionSince` (the page says "Offline since" from it).
