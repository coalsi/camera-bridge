# BridgeWeb

The web interface of Camera Bridge OS, as portable Swift: an HTTP/1.1 server over the injected `NetworkTransport`, the JSON API
(`/api/v1`), password and session handling, static file serving and an SVG QR code encoder. It depends on the engine and on
`Crypto` only; every test runs on a Mac against a fake backend, the in-memory transport or the real engine. The API contract is
in `docs/linux/ARCHITECTURE.md`; the interface itself is `linux/web/`.

## Layout

| File | What |
|---|---|
| `HTTPServer.swift`, `HTTPTypes.swift` | Keep-alive and pipelined requests (parsed by BridgeSupport's `HTTPRequestParser`), head, body and time limits, connection limits per peer, chunked streaming answers (server-sent events, multipart JPEG) that end when the client leaves |
| `WebApp.swift`, `WebApp+Routes.swift`, `WebApp+Bridge.swift` | The route table and handlers; Host, Origin, session and CSRF checks; security headers |
| `AuthStore.swift`, `Security.swift` | First-run setup, PBKDF2-HMAC-SHA256 (600,000 rounds, per-password salt), 256-bit session tokens kept as SHA-256 hashes in `<data>/web/auth.json` (0600), login rate limiting, constant-time comparison |
| `CameraSetup.swift`, `CameraTypeCatalog.swift`, `HostInput.swift` | The Mac app's Add Camera wizard as a stateless service: the same types, words and checks |
| `EventHub.swift`, `LogFeed.swift` | Server-sent events from the engine's observable state; the live log |
| `StaticFiles.swift` | The interface's files: content types, ETag and 304, traversal-proof paths |
| `QRCode.swift` | QR Code encoder (byte mode, versions 1 to 10, levels L and M) drawing SVG |
| `BridgeBackend.swift`, `SystemControl.swift` | The seams: `EngineBackend` wraps `BridgeEngine`; `SystemControlling` is the operating system under the bridge |
| `WebApp+NVR.swift`, `WebApp+NVRStorage.swift`, `WebApp+NVRCatalog.swift`, `WebApp+NVRMedia.swift`, `WebApp+NVROptimize.swift`, `ArchiveLocation.swift` | The NVR routes: the route table (`WebApp.archiveRoutes`), admission slots, the gates and the one error mapping; storage and the Record switch; catalog, activity and events; fragment plans, video-only fragments, init segments and key pictures; the optimizer and its undo; the places the page may offer for recordings (`ArchiveLocation`: the browser sends the id and never the path) |
| `WebApp+Sky.swift` | The Sky Watcher's routes (`WebApp.skyRoutes`: the night's log, an entry's picture, one-tap corrections, "Find a feed"), what `PATCH settings` and `PATCH cameras/:id` take for it (`SkyPatch`, `SkyDetectorPatch`) and what the page reads (`SkyNightResource`, `SkyEntryResource`, `SkySettingsResource`) |

## Additions beyond the contract

Camera detection (2026-10-23, docs/CONTRACT_CHANGES.md): `POST probe` answers `ownInterfaceNote` when an ONVIF camera was added through its maker's own interface ("Found Hikvision's own interface (ANNKE I91ET); using it for settings and security.", `NotSetUpText`), and a failed check of a camera with no admin password yet answers `notSetUp` `{maker, title, step, webPage, openLabel, checkAgainLabel}` (`BridgeBackend.notSetUp(endpoint:)`, asked without a login); a Reolink answering with an empty password gets the same card. The page (`screens/not-set-up.js`) shows the step with "Open the camera's web page" and "Check again".

Camera search (2026-10-24, docs/CONTRACT_CHANGES.md): each camera of `POST discover` may carry `otherNetwork` `{address, title, step, checkAgainLabel}` (Hikvision's SADP found it on none of the box's networks: "Found a camera on another network (192.168.1.64)", with what to do: SADP tool or a computer on that network, turn on DHCP, then Check again; `NotSetUpText.otherNetwork`) or `notSetUp` (SADP says it has no admin password yet: the same card as the check's, its `webPage` at SADP's `HttpPort`). The Add camera page's search (`screens/add.js`, `otherNetworkCard` in `screens/not-set-up.js`) shows those cameras as cards, not as choices; Check again searches again. Tests: `DiscoveryAPITests`, `linux/web-tests/not-set-up.test.mjs`.

Camera events (2026-10-16, docs/CONTRACT_CHANGES.md): route `GET nvr/events?cameras=&from=&to=&limit=` (`WebApp+NVRCatalog.swift`, in `archiveRoutes`): the archive's events through `ArchiveReading.events(cameras:range:limit:)`, newest first, at most 1000 (a page never splits a millisecond), gated and admitted like `activity`, `503 archive_unavailable` with `Retry-After` for `ArchiveUnavailable` (loading, folder missing); the answer and the event log's format are in `docs/linux/ARCHITECTURE.md`.

Straighten the picture, the setting (2026-10-18, docs/CONTRACT_CHANGES.md): a camera's resource carries `pictureCorrection` `{straighten, level}` (`CameraConfiguration.pictureCorrection`, `{0, 0}` = off) and `PATCH cameras/:id` takes it as a whole value (`WebApp+Routes.swift`, `CameraPatch.pictureCorrection`): numbers past the limits (±0.60, ±0.40) are clamped, never refused, a missing key counts as 0, and a change never restarts the camera. The page's card is `linux/web/js/screens/camera.js`, its drawing `linux/web/js/live/straighten.js`.

Time-lapse clips (2026-10-24, docs/CONTRACT_CHANGES.md): `speed=30|60|120|300` on the clip route (`WebApp.timelapseSpeed`; anything else is 400 `invalid` with field `speed`) re-encodes the clip through the same path as labelled and straightened clips (`processedClip`, the `maximumClipConversions` slots, `nice -n 10`): ffmpeg decodes the key pictures only (`-skip_frame nokey` on the input), draws the label (when `labels=1`) at their real times, then `setpts=(PTS-STARTPTS)/speed,fps=30` (`WebApp.timelapseFilters`, `timelapseFrameRate`), and writes no sound (`-an`); straightening applies as for any clip. The file is named `… time-lapse 60x.mp4` (`WebApp.timelapseFileName`). Without ffmpeg the answer is 501 "This bridge has no video converter for time-lapse clips.". `clipArguments(…, speed:)` takes the speed (default nil: the arguments are the old ones, argument for argument).

Straighten the picture, saved clips (2026-10-18, docs/CONTRACT_CHANGES.md): `straighten=1` on the clip route (`WebApp+NVRClipLabels.swift`, now the path of every re-encoded clip): while the camera's `pictureCorrection` is on, the clip is warped by the transcoder's per-plane `remap` chain at the clip's size (`MediaFit.cappedEvenSize`: at most 3840 wide, the height in proportion and even, the rule the live transcoders use too; maps written in the clip's private temporary folder), the label drawn after it when `labels=1` too; otherwise the clip is copied as recorded. `clipArguments` replaces `labelArguments` (unchanged arguments without a correction). At most `WebApp.maximumClipConversions` (2) re-encoded clips are converted at once, box-wide (`ConversionSlots`): a further download keeps its archive slot, has its response head sent and waits for a place with nothing written (its browser leaving ends the wait), so a clip bar with several cameras ticked does not take the box's cores from the live video; and on Linux ffmpeg runs under `nice -n 10` (`WebApp.conversionCommand`).

Straighten the picture, snapshots (2026-10-18, docs/CONTRACT_CHANGES.md): `BridgeBackend.snapshotJPEG(cameraID:original:)` replaces `snapshotJPEG(cameraID:)` (`EngineBackend` calls `BridgeEngine.snapshot(cameraID:original:)`); `GET cameras/:id/snapshot` (and `live`) answer the picture straightened by the camera's `pictureCorrection`, and `GET cameras/:id/snapshot?original=1` (and `live?original=1`) the camera's own picture, for the camera page, which straightens it itself while its sliders move.

  and `PATCH cameras/:id` refuses `skyDetector.enabled: true` (400, field `plugins.sky`, "Turn on Sky Watcher in Plugins first.", checked before the camera, the

  on again brings the same cameras back. The box's own Sky Watcher settings (where it is, the flight feed, the AI's daily limit) are set in a Setup panel at the top of

- The Sky Watcher (2026-10-25, docs/CONTRACT_CHANGES.md; `WebApp+Sky.swift`, `WebApp.skyRoutes` in the route table): `BridgeBackend.skyNightLog(cameraID:night:view:)`, `BridgeBackend.correctSkyEntry(cameraID:entryID:night:label:)`, `BridgeBackend.skyStill(cameraID:night:entryID:)` and `BridgeBackend.findFlightFeeds()` (requirements with extension defaults: `SkyLogError.unavailable`, and no feeds; `EngineBackend`, `NoArchiveBackend`, `DemoDiscoveryBackend` and the tests' `FakeBackend` forward or implement them) reach the engine's sky log. Every route needs a session, and times are epoch milliseconds. Routes: `GET sky/cameras/:id/night?date=yyyy-MM-dd&view=night|day` answers `{camera, night, view, from, to, serverTime, entries, conditions, counts, aim, learning, capped}` (no `date`: the latest; no `view`: the night; each entry carries `display`, the label the log shows, and `watch`, the recordings' moment to open, 3 s before it began; `capped` (2026-10-25, `SkyNightResource.Capped`) is `[{hour, count}]`, the clock hours of the view in which the camera followed more lights that nothing explains than the 60 it logs an hour, and how many more; an optional value is `null`, never left out; 400 with the field `date` or `view`, 404 for an unknown camera, `409 no_location` or `no_folder` with the sentence to show, `503`/`504` while the recordings' drive is away or slow); `GET sky/cameras/:id/entries/:eid/still?night=` answers `image/jpeg` (`private, max-age=3600`; 404 without one, 400 with the field `night`); `POST sky/cameras/:id/entries/:eid/correction` `{night, label}` (`plane`, `bird`, `bug`, `satellite`, `meteor`, `notSure`) answers the entry (400 with the field `label` or `night`, 404 for an entry the log does not hold); `POST sky/feeds/find` answers `{feeds: [url]}`, one address per host. Settings: `GET settings` carries `sky` `{location: {latitude, longitude, heightMeters} | null, flightFeedURL | null, aiDailyLimit}` (the place is shown here, to the signed-in page, and nowhere else: not in the cameras' list, the status, the event stream or any log line), and `PATCH settings` takes `sky` (`location` as `{latitude, longitude, heightMeters?}` or `null`, `flightFeedURL` as a string or `null`, `aiDailyLimit`; what is left out stays, `null` takes the place or the feed away, a place is replaced whole; 400 with the field `sky.location`, `sky.flightFeedURL` or `sky.aiDailyLimit`, in words that never repeat what was sent). A camera's resource always carries `skyDetector` (the saved settings, or `null`), and `PATCH cameras/:id` takes `skyDetector` `{enabled, facing, tilt, groundPercent, nightProfile, lensLayout}` (a field left out stays; `lensLayout` `null` is automatic; 400 with the field `skyDetector.facing`, `.tilt`, `.groundPercent` or `.lensLayout`). Saying `enabled: true` is refused with 400 and a sentence for the person when the Sky Watcher plugin is off ("Turn on Sky Watcher in Plugins first.", field `plugins.sky`), the camera streams only on demand ("Battery cameras can’t watch the sky: it would keep them awake.", field `skyDetector.enabled`), the box does not know where it is ("Set where the box is first.", field `sky.location`) or no recordings folder is chosen ("Choose a recordings folder first: the sky log is kept with the recordings.", field `nvrFolder`), in that order; turning it off, and changing the aim of a camera without saying "on" again, need none of them. Sky Watcher is a plugin (2026-10-25, below): `GET plugins` lists it as the third, `PATCH plugins/sky {enabled}` is its switch (`BridgeSettings.plugins["sky"]`, off on a new box; `BridgeSettings.skyPluginOn`), and every camera keeps its `skyDetector` settings while it is off. Internal: `SkyEntryResource`, `SkyMeasuresResource`, `SkyNightResource`, `SkySettingsResource`, `SkyPatch`, `SkyDetectorPatch`, `SkyWatcherPlugin`. Requests and answers are in `docs/linux/ARCHITECTURE.md`; tests: `SkyAPITests`. ## Security notes

- Only IP addresses, `localhost`, `*.local`, `*.home.arpa`, names without a dot and `allowedHosts` are served (DNS rebinding).
- A request that changes something needs an `Origin` that matches `Host` (or `Sec-Fetch-Site: same-origin`), the session's
  `X-CSRF-Token` and `Content-Type: application/json`.
- The session cookie is `HttpOnly; SameSite=Strict; Path=/` (and `Secure` behind a TLS front end).
- Recordings: every NVR route needs a session. The browser sends ids and times, never a path (a location is an opaque id from `WebConfiguration.archiveLocations`, a fragment
  id is opaque). Footage is `Cache-Control: no-store`, an answer is at most `maximumSegmentBytes`, there is no `Range` support and HEAD on a media route is 405. Archive
  requests are admitted at most `maximumArchiveReads` in all and `maximumArchiveReadsPerAddress` per peer address (`429 busy`, `Retry-After: 1`), and no handler touches the
  disk on the cooperative pool.
- The Content-Security-Policy allows `media-src 'self' blob:` and nothing else beyond what the interface already had: the player's MediaSource URL is a `blob:`; no script, frame, worker or remote host is widened.
- Camera passwords, cloud sources and API keys go to the engine's secret store and never into an answer, the log or a file of the web
  interface.

Notifications (2026-10-22, docs/CONTRACT_CHANGES.md; `NotificationLog.swift`, `WebApp+Notifications.swift`): the log of everything that was a notice, in `notifications.json` in the data directory (private file, written atomically; the last 500 entries or 90 days). An entry is added when a notice first appears or changes (`NoticeResource.key`: its id, title and camera, so other figures in the text are not a change); a state notice that goes away and comes back is a new entry, an event (the Internet guard's, `kind` `internetGuard`) is logged once ever (the keys of the last 1000 events are kept). The log is brought up to date by the event hub on every change it sees (and every 5 s while nobody listens) and by each of the routes. `GET notifications` lists it (`{unread, notifications}`, newest first); `POST notifications/shown` hands the entries of the current notices not yet shown as a toast to the caller and marks them shown, so each is shown once by one browser (the phone and the Mac agree; nothing is kept in the browser); `POST notifications/read {ids?}` marks entries read, or all. An entry: `id, key, noticeID, kind, category (security|recording|cameras|system), severity, title, detail, cameraID, cameraName, action, date, read, toasted`. `status.notices` items carry `category` and `key` too, and no longer a `cameras` list.
